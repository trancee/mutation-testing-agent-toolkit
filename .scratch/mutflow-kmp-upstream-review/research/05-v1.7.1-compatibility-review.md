## 3. What changed, semantically: the `kotlin-stdlib`-floor fix

### The bug being fixed

`MutflowGradlePlugin.kt` adds `mutflow-annotations` to a consuming project via Gradle's `"implementation"` configuration (confirmed directly in source, [`MutflowGradlePlugin.kt`](https://github.com/anschnapp/mutflow/blob/v1.7.1/mutflow-gradle-plugin/src/main/kotlin/io/github/anschnapp/mutflow/gradle/MutflowGradlePlugin.kt) lines 142-144 and 258-260 for the plain-JVM and KMP wiring paths respectively). Because `implementation` dependencies land on the runtime classpath (even though hidden from downstream compile-time API), and because the Kotlin Gradle Plugin auto-adds a default `kotlin-stdlib` dependency at the exact `coreLibrariesVersion` a published artifact's own build used (`2.4.20` for `1.7.0` and earlier `1.7.x`), any consumer project built with Kotlin `2.4.0`–`2.4.19` would have its own resolved `kotlin-stdlib` silently raised to `2.4.20` by adding the mutflow plugin — the exact defect upstream's own `CHANGELOG.md` describes.

### The fix

New root `build.gradle.kts` `subprojects {}` block ([patch](https://github.com/anschnapp/mutflow/commit/b284d3edbd9c3a1ec6f525284a4a2c81541aeeb0), full context at [v1.7.1](https://github.com/anschnapp/mutflow/blob/v1.7.1/build.gradle.kts)):

```kotlin
subprojects {
    // Publish against the lowest supported stdlib, so consumers keep their own 2.4.x
    // instead of being raised to the version mutflow happens to be built with.
    listOf("org.jetbrains.kotlin.jvm", "org.jetbrains.kotlin.multiplatform").forEach { id ->
        plugins.withId(id) {
            extensions.configure<org.jetbrains.kotlin.gradle.dsl.KotlinProjectExtension> {
                coreLibrariesVersion = property("kotlinStdlibVersion").toString()
            }
        }
    }
    // ... (unchanged jvmTarget/sourceCompatibility blocks follow)
}
```

driven by a new property in [`gradle.properties`](https://github.com/anschnapp/mutflow/blob/v1.7.1/gradle.properties):

```
kotlinVersion=2.4.21
# Minimum kotlin-stdlib consumers get from mutflow's published metadata
kotlinStdlibVersion=2.4.0
junitVersion=6.1.3
junit4Version=4.13.2
serializationVersion=1.12.0
```

This uniformly lowers the published `kotlin-stdlib` floor for every Kotlin JVM/MPP subproject to `2.4.0` (the first patch of the `2.4` minor) — independent of the Kotlin compiler version (`2.4.21`) mutflow itself is built and published with.

### Independent verification this is genuine Kotlin Gradle Plugin API, not an invented hack

`coreLibrariesVersion` is a real, public, `@KotlinGradlePluginPublicDsl`-annotated property on the Kotlin Gradle Plugin's project extension — confirmed directly in `JetBrains/kotlin` at tag `v2.4.21`:

- [`KotlinProjectExtension.kt`](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/dsl/KotlinProjectExtension.kt):100 — `override lateinit var coreLibrariesVersion: String`.
- [`stdlibDependencyManagement.kt`](https://github.com/JetBrains/kotlin/blob/v2.4.21/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/internal/stdlibDependencyManagement.kt):39-50 — `internal fun Project.configureStdlibDefaultDependency(kotlinExtension: KotlinProjectExtension, coreLibrariesVersion: Provider<String>)`, which calls `target.addStdlibDependency(configurations, dependencies, coreLibrariesVersion, ...)` for every Kotlin target — this is the actual mechanism that makes `coreLibrariesVersion` drive the default `kotlin-stdlib` dependency version written into a published project's dependencies (and hence its POM/module metadata).

This confirms the fix uses a documented, intended Kotlin Gradle Plugin extension point for exactly this purpose, not an undocumented workaround.

## 5. Practical impact on this toolkit's own dependency resolution — a reasoned inference, explicitly not an executed check

The toolkit's own Kotlin pin is `2.4.21` (`sample/build.gradle.kts`, committed `HEAD`).
