## Verdict (TL;DR)

1. **MutFlow `v1.7.0` is real, fully merged to `master`, CI-green on every PR, and published to Maven Central for all five consumer artifacts.** `v1.7.0` (`66af91aadfe97f1b997fa6055a3ce89428a2905c`) and `master` are byte-identical — 0 commits ahead or behind in either direction, re-confirmed independently in this review. §1, §7.
2. **The `v1.6.2→v1.7.0` diff is 11 commits / 34 files and carries exactly two behavior-affecting features**, each merged through its own PR with a green `ci.yml` run on the PR's final commit: (a) [#28](https://github.com/anschnapp/mutflow/pull/28) adds a fourth case, `ACCUMULATE`, to the **pre-existing** `VerificationMode` enum, plus a `mutflowAccumulateReport`/`mutflowAccumulateTest` task pair that merges per-test-class verdicts; (b) [#41](https://github.com/anschnapp/mutflow/pull/41) changes the **display name** of a removed-lambda mutation from `<anonymous>() → removed` to the enclosing call/declaration, e.g. `onEach {} → removed` — upstream's own `CHANGELOG.md` states point IDs are unchanged, only the display string differs. §2, §3.
3. **Both features are inert under this toolkit's current and in-progress configuration.** `ACCUMULATE` is gated behind an explicit opt-in (`MUTFLOW_VERIFICATION_MODE=ACCUMULATE` env var or `mutflow { verificationMode = ... }` DSL) in all three places it was wired (plain-JVM Gradle plugin, KMP Gradle plugin, JUnit 4 runner); the default is `STRICT`, and neither the sample nor any script/doc in this repository sets `verificationMode`, `ACCUMULATE`, or `failOnSurvivors` anywhere — confirmed by a repository-wide search that returns zero hits outside an unrelated, older `.scratch/scott-cc-comparison` research note describing a pre-1.6.2 mutflow fork (not toolkit source or configuration). The lambda-naming change only affects a free-text display string; the toolkit's own `MutationResultsParser.kt:33` regex is generic (not anchored to `<anonymous>`) and no fixture asserts the old string. §4.
4. **Dependency-pin and artifact compatibility is unchanged.** `gradle.properties` is byte-identical between the two tags (`kotlinVersion=2.4.20`, `junitVersion=6.1.3`, `junit4Version=4.13.2`, `serializationVersion=1.11.0`); all five Maven Central `.pom` files are byte-identical to their `1.6.2` counterparts once the version string itself is normalized out; `mutflow-gradle-plugin-1.7.0.pom` still depends on `kotlin-stdlib:2.4.20` / `kotlin-gradle-plugin-api:2.4.20`; and the Gradle Module Metadata variant sets published for `mutflow-core`/`mutflow-runtime` (`jvm`, `linuxX64`, `mingwX64`, plus `metadata*`) are identical at both versions. **MutFlow 1.7.0 does not require moving this toolkit's Kotlin pin.** §5.
5. **The Kotlin `2.4.21` finding is an independent, unrelated signal — not a side effect of the mutflow bump.** `kotlin-gradle-plugin`'s raw Maven Central `<latest>`/`<release>` tags actually point to the prerelease `2.5.0-Beta1`; `scripts/check-upstream.py`'s stable-only filter (full-match regex excluding hyphenated suffixes) correctly resolves `2.4.21` as the latest *stable* release. That release was published **2026-10-08**, one day *after* mutflow's `v1.7.0` tag (`2026-10-07T17:42:04Z`), by an unrelated team (JetBrains), independently confirmed against the `JetBrains/kotlin` tag `v2.4.21`. Upstream mutflow 1.7.0 itself still targets Kotlin 2.4.20. §6.
6. **This repository already has an in-progress, uncommitted migration** on the checked-out branch `chore/mutflow-1.7.0` (`HEAD` unchanged at the merge commit `22f59f08d...`): 18 modified, 0 new files, performing a pure `1.6.2`→`1.7.0` string substitution in the two canonical pin files, two test-harness scripts, and ~11 docs/profile files. The Kotlin pin (`2.4.20`) is untouched everywhere in that diff. Re-running `scripts/check-upstream.py` (`--offline` and online, both read-only) against this exact working tree in this review confirms **zero mutflow-related drift findings remain** — the only surviving finding is the independent Kotlin-2.4.21 advisory from point 5. §8.
7. **Compatibility limit of this review:** all verification here is evidence-level — upstream source/diff reading, published-artifact/POM/module comparison, CI check-run status, and a live, read-only re-run of the toolkit's own drift checker against the dirty working tree. **No Gradle build or mutation run was executed** by this session against the sample with 1.7.0 wired in. ## 1. `v1.7.0` is tagged, CI-green, and separates PR-time testing from tag-time publish

Upstream `anschnapp/mutflow` remains a **tag-only** release process: the Releases API returns **zero** Release objects for the whole repository, exactly as observed for `v1.1.1`–`v1.6.2` in notes 01–03. All release signal lives in tags and the modern check-runs API; the legacy combined Status API on the tag commit returns `{"state":"pending","total_count":0}` (unused).

The CI topology is unchanged from note 03's description and is re-confirmed here at `v1.7.0`:
- [`ci.yml`](https://github.com/anschnapp/mutflow/blob/v1.7.0/.github/workflows/ci.yml) triggers only on `pull_request` targeting `master`; its `build` job runs `./gradlew build` then `scripts/test-mutflow-verify-jar.sh`.
- [`publish.yml`](https://github.com/anschnapp/mutflow/blob/v1.7.0/.github/workflows/publish.yml) triggers only on tag push (`v*`); its `publish` job runs `./gradlew publishAndReleaseToMavenCentral --no-configuration-cache -PreleaseVersion=...` and does **not** invoke `check` or any test task.

> ## [1.7.0]
> ### Changed
> - The body removal of a Unit lambda is named after the call it is passed to or the variable or property it initialises: `(Screen.kt:92) onEach {} → removed` instead of `<anonymous>() → removed`, also for a lambda converted to a Java or `fun interface` type. >
> ### Added
> - `VerificationMode.ACCUMULATE` and the `mutflowAccumulateReport` Gradle task: a merged verdict across test classes. A single test class cannot tell whether a survivor is a real gap when other classes exercise the same production code. In `ACCUMULATE` mode no class judges its survivors; each writes every mutation it reached with its verdict to `build/mutflow/results/<TestClass>.json` ..., and `mutflowAccumulateReport` (`mutflowJvmAccumulateReport` for a multiplatform `jvm()` target) merges them: killed by any class wins, a timeout counts as killed, a mutant survives only if no class that reached it killed it. It writes `build/reports/mutflow/mutation-report.md` ... and fails the build on survivors unless `mutflow { failOnSurvivors = false }`. ... The tasks exist only in `ACCUMULATE` mode: a plain JVM project gets `mutflowAccumulateTest` to run the mutations, and its ordinary `test` task runs the baseline only. Classes on the JUnit 4 runner take part the same way as `@MutFlowTest` classes. (#24)
>
> ### Contributors
> Thanks to @rikshot for both changes in this release, above all `ACCUMULATE`, which tells a real gap from a survivor another test class covers. ...

The emphasis above (bold) is this review's own, added to highlight upstream's explicit compatibility caveat about display-name diffing, addressed in §4.

## 3. Feature A — `ACCUMULATE` extends a pre-existing enum; it is not a new concept

`VerificationMode` (`STRICT`/`LENIENT`/`DISABLED`) **predates this diff** — it is not introduced by 1.7.0. This toolkit's own (older, unrelated) `.scratch/scott-cc-comparison/research/02-comparison-matrix.md:155` research note independently documents this same enum as already present upstream as of mutflow `v1.1.1`, well before the `1.6.2`→`1.7.0` window reviewed here. PR #28 adds a **fourth** case to the existing enum:

`MutFlow.kt:429-458` ([v1.7.0](https://github.com/anschnapp/mutflow/blob/v1.7.0/mutflow-runtime/src/commonMain/kotlin/io/github/anschnapp/mutflow/MutFlow.kt#L429-L458)):
```kotlin
enum class VerificationMode {
    /** Surviving mutations cause test failure. This is the default mode ... */
    STRICT,
    /** Surviving mutations are reported in the summary but do not cause test failure. ... */
    LENIENT,
    /** Mutation runs are skipped entirely — only the baseline (regular tests) runs. ... */
    DISABLED,
    /**
     * Mutations run, but no test class judges its survivors: each class writes
     * what it saw to a results file (see [MutFlow.closeSession]), and the Gradle
     * `mutflowAccumulateReport` task merges those across classes and gives the
     * verdict. ...
     */
    ACCUMULATE
}
```

Supporting mechanics, all read directly from the `v1.7.0` tag:
- `MutFlow.createSession()` gains two trailing, defaulted, source/binary-compatible parameters — `testClassName: String = ""`, `resultsDirectory: String? = null` (`MutFlow.kt:54-88`). The toolkit never calls `MutFlow`'s API directly (confirmed by a repository-wide grep returning zero hits); it only consumes mutflow as a black-box Gradle-plugin/JUnit-integration dependency, so this signature widening cannot affect the toolkit.
- `MutFlow.closeSession()` now calls `session.writeResults()` after `printSummary()` (`MutFlow.kt:98` and surrounding). `MutFlowSession.writeResults()` (`MutFlowSession.kt:639-648`) begins with `if (verificationMode != VerificationMode.ACCUMULATE) return` — a guaranteed no-op under every other mode, including the toolkit's default `STRICT`.
- `MutFlowSession.collectResults()` (`MutFlowSession.kt:608-630`) builds the per-class JSON record list consumed only by `writeResults()`, which is itself gated as above.
- Default DSL convention: `extension.verificationMode.convention("STRICT")` (`MutflowGradlePlugin.kt:120`), `extension.failOnSurvivors.convention(true)` (`MutflowGradlePlugin.kt:124`) — `failOnSurvivors` only has an effect on the `mutflowAccumulateReport` task, which itself only exists when `ACCUMULATE` is active (§4).

## 4. Feature B — lambda-naming changes a display string only; toolkit's parser is unaffected

Implemented in `MutflowIrTransformer.kt` (`v1.7.0`):
- A new `lambdaNames: MutableMap<IrFunction, String>` (`IdentityHashMap`) field (`MutflowIrTransformer.kt:245`).
- `recordLambdaName(expression, name)` (`MutflowIrTransformer.kt:247-256`), invoked from new `visitVariable`/`visitField` overrides (`MutflowIrTransformer.kt:258-265`) and from a call-argument visit (`MutflowIrTransformer.kt:460`).
- Consumed in `transformFunctionBody` via `mutationContext(declaration).copy(lambdaName = lambdaNames[declaration])` (`MutflowIrTransformer.kt:840`).
- `MutationOperator.kt:52` adds `val lambdaName: String? = null` to the mutation context data class.
- `VoidFunctionBodyOperator.kt:53` is the only read site: `originalDescription = context.lambdaName?.let { "$it {}" } ?: "${node.name}()"` — this is purely a label-formatting change for one specific operator (void-lambda-body removal); it does not touch mutation point IDs, discovery, or any other operator.

This toolkit's own JUnit-XML display-name parser, `sample/buildSrc/src/main/kotlin/ch/trancee/mutation/MutationResultsParser.kt:33`, uses the generic regex:
```
"""([✓✗⏱])\s*\(([^)]+)\)\s+(.+?)\s*(?:→|->)\s*(.+)"""
```
This pattern captures the "before" segment as `(.+?)` (non-greedy, any text) — it is **not** anchored to the literal string `<anonymous>` and requires no changes to continue matching `onEach {} → removed` exactly as it previously matched `<anonymous>() → removed`. No fixture in `MutationResultsParserTest.kt`/`JUnitMutationReportTest.kt`/`MutationResultsSummaryTest.kt` asserts the literal `<anonymous>` string (confirmed by inspection of the test files alongside the parser). The toolkit also does not persist or diff a historical baseline keyed by display name across runs — it parses only the current run's JUnit XML each time — so upstream's own compatibility caveat ("results compared across runs by display name see the new names," quoted in §2) does not apply to how this toolkit consumes mutflow's output today.

**Repository-wide confirmation that neither feature's API surface is referenced:** a search across all `*.kt`, `*.kts`, `*.py`, `*.sh`, and `*.md` files in this repository for `VerificationMode`, `ACCUMULATE`, and `failOnSurvivors` returns **zero** hits in any toolkit source, build script, CI workflow, bootstrap script, test harness, or documentation file. The only repository hits for these terms at all are two lines in `.scratch/scott-cc-comparison/map.md:58` and `.scratch/scott-cc-comparison/research/02-comparison-matrix.md:99,155` — a separate, older research series comparing mutflow against an unrelated product, describing a **pre-1.6.2** mutflow fork's `VerificationMode` (STRICT/LENIENT/DISABLED only, no `ACCUMULATE`). These are historical analysis notes, not toolkit source or configuration, and are unrelated to the `mutflow-kmp-upstream-review` series or to this compatibility question.

## 6. Kotlin 2.4.21 is an independent, unrelated signal

`scripts/check-upstream.py:14-21` declares the Maven coordinate under test for the `kotlin` pin as `org.jetbrains.kotlin/kotlin-gradle-plugin`. The raw `maven-metadata.xml` for that coordinate currently reports:
```xml
<latest>2.5.0-Beta1</latest>
<release>2.5.0-Beta1</release>
<lastUpdated>20261008081250</lastUpdated>
```
(`2.5.0-Beta1` is a **prerelease**.) `scripts/check-upstream.py:95-99` deliberately does not trust this raw tag; it instead filters the full `<versions>` list with a full-match regex that rejects any hyphenated suffix:
```python
stable = [
    node.text for node in metadata.findall("./versioning/versions/version")
    if re.fullmatch(r"\d+(?:\.\d+)+", node.text or "")
]
latest = max(stable, key=lambda version: tuple(map(int, version.split("."))))
```
This correctly resolves to `2.4.21` as the latest **stable** release — the same value the triggering workflow run and this review's own replay report. The artifact files for `kotlin-gradle-plugin-2.4.21` (e.g., the `gradle80`/`gradle81` jar variants) carry a directory-listing timestamp of **2026-10-08 07:57 UTC**; the aggregate `maven-metadata.xml`'s own `lastUpdated` stamp is **2026-10-08T08:12:50Z**. This was independently cross-checked against the `JetBrains/kotlin` repository's own tag: `v2.4.21` → commit `9180ce6a7a7d3627f88b424717583f28ddca052d` ([ref](https://github.com/JetBrains/kotlin/releases/tag/v2.4.21)).

Kotlin `2.4.21` is published by JetBrains, an unrelated team, on an unrelated schedule, one day after mutflow's own release. Mutflow `1.7.0` itself — per its own `gradle.properties` and all five published POMs (§5) — still targets Kotlin `2.4.20`. Bumping the toolkit's mutflow pin from `1.6.2` to `1.7.0` neither causes nor resolves the Kotlin `2.4.20`-vs-`2.4.21` finding; they are two independent upstream signals that happened to be collected in the same scheduled run.
