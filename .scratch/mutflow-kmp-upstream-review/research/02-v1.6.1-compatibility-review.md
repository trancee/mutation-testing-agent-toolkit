# Is MutFlow 1.6.1 Compatible, and Is the Upstream Monitor's Failure a Bug? (Issue #11 Research)

**Trigger:** Scheduled "Upstream synchronization" run [`37204742480`](https://github.com/trancee/mutation-testing-agent-toolkit/actions/runs/37204742480) (event `schedule`, `main` SHA `320e5d8435e024dbfc4e61461f74ee9a56e816eb`) failed its `Verify latest stable versions and upstream API drift` step and opened/updated [`trancee/mutation-testing-agent-toolkit#11`](https://github.com/trancee/mutation-testing-agent-toolkit/issues/11) with three `[upstream]` messages: `mutflow` stable is 1.6.1 (toolkit pins 1.6.0), `mutflow-junit4` stable is 1.6.1 (toolkit pins 1.6.0), and upstream `master` differs from `v1.6.0`. The parent reproduced this on current `main` (`40c5bb5`, a no-op merge w.r.t. this logic — see §6) and asked three things: (a) is 1.6.1 compatible with the toolkit's pinned Kotlin 2.4.20 / JUnit 6.1.3 / JUnit4 path, (b) exactly what changed 1.6.0→1.6.1, (c) is the workflow failure the intentional guard or a bug.

**Sources consulted (first-party only):** `anschnapp/mutflow` GitHub repo (tags, refs, compare API, raw file contents, commit check-runs) and `repo.maven.apache.org` (Maven Central `maven-metadata.xml` and `.pom` files) — the exact same endpoints `scripts/check-upstream.py` itself queries. No upstream scripts were executed.

## Verdict (TL;DR)

1. **Not a bug — the guard is correct and all three messages are mechanically true.** `scripts/check-upstream.py:2` states its purpose plainly: *"Fail visibly on upstream drift, mismatched pins, or stale generated sources."* Maven Central's `maven-metadata.xml` for both `mutflow-gradle-plugin` and `mutflow-junit4` genuinely lists `<release>1.6.1</release>` (§2), and `anschnapp/mutflow`'s `master` genuinely is not `v1.6.0` (§3). Exit code 1 and the GitHub issue are the designed response (`check-upstream.py:112-115`), not a malfunction.
2. **1.6.1 is compatible with the toolkit's pins.** `v1.6.1`'s `gradle.properties` declares `kotlinVersion=2.4.20`, `junitVersion=6.1.3`, `junit4Version=4.13.2` — byte-identical to `v1.6.0`'s and to the toolkit's own pins in `sample/build.gradle.kts` and `.mutation-testing/mutation-results-src/build.gradle.kts` (§4). The published POMs for `mutflow-gradle-plugin`, `mutflow-junit4`, and `mutflow-junit6` (the module that backs the "generated JUnit 6 integration," including for KMP JVM targets) are identical between 1.6.0 and 1.6.1 except for the version string itself (§4-5).
3. **The 1.6.0→1.6.1 diff touches nothing the toolkit depends on.** It is a single, narrow compiler-plugin bugfix (4 commits, 5 files) to the boolean-inversion mutation operator, plus its own CHANGELOG/README/test-fixture updates. It does **not** touch `mutflow-gradle-plugin`, `mutflow-junit4`, `mutflow-junit6`, the DSL (`MutflowExtension`), or `DESIGN-MULTIPLATFORM.md` (§3).
4. **"Master differs from v1.6.0" is not separate/unreleased risk — it is the same drift restated.** `anschnapp/mutflow` `master` HEAD (`961fb2b7e88724432f919b2e2df82045d507e45d`) is **exactly** the `v1.6.1` tag commit: `compare/v1.6.1...master` returns `"status":"identical","ahead_by":0,"total_commits":0` (§6). There is zero untagged/undocumented code on `master`. The third monitor message fires purely because the pin (`v1.6.0`) is one release behind `master`/`v1.6.1`, and it will self-resolve the moment the pin is bumped — it is not evidence of hidden, unreleased API drift beyond what messages 1-2 already report.
5. **One cosmetic (non-functional) nuance worth flagging to maintainers:** the `"Verified upstream mutflow v1.6.0, release commit ..."` line (`check-upstream.py:110`) is printed **unconditionally**, before the script knows whether `errors` is non-empty, and reads like a success confirmation even when the run fails. It appears *after* the three `[upstream]` stderr lines in the combined `upstream-status.txt`/issue body purely because of Python stdio buffering (stdout is block-buffered when redirected to a file; stderr is not), not because of execution order. This does not affect detection correctness or the exit code, but could be reworded to avoid reading as self-contradictory (see §7).

## 3. The exact 1.6.0→1.6.1 diff

`GET /repos/anschnapp/mutflow/compare/v1.6.0...v1.6.1` → `"status":"ahead","ahead_by":4,"total_commits":4"`, touching exactly 5 files:

| File | Nature of change |
|---|---|
| `CHANGELOG.md` | Adds the `## [1.6.1]` entry (quoted below) |
| `README.md` | One sentence added to the "Discarded results are not inverted" doc paragraph |
| `mutflow-compiler-plugin/src/main/kotlin/io/github/anschnapp/mutflow/compiler/MutflowIrTransformer.kt` | The actual fix (below) |
| `mutflow-test-sample/src/main/kotlin/sample/DiscardedResultTarget.kt` | New fixture methods for the fix's test cases |
| `mutflow-test-sample/src/test/kotlin/sample/DiscardedResultTargetTest.kt` | New tests for the fixture methods |

CHANGELOG (`anschnapp/mutflow:CHANGELOG.md` at `v1.6.1`, `## [1.6.1]`):
> Boolean inversion no longer mutates a call whose result is the discarded value of a scope function, `synchronized` or `use`. In `x?.let { list.add(it) }` as a statement, `add` is the lambda's last expression, so it was taken for a used result and inverted, although its value only becomes the value of `let`, which nobody reads: an equivalent mutant that every test class reaching the line had to run and none could kill. A discarded `let`, `run`, `with`, `synchronized` or `use` now marks what its lambda returns... as discarded too... Other functions that take a lambda are unchanged: `items.any { seen.add(it) }` reads the lambda's result, so its inversion stays.

The code change (`mutflow-compiler-plugin/.../MutflowIrTransformer.kt`, diff hunk) adds a `lambdaValueFunctions` set (`kotlin.let`, `kotlin.run`, `kotlin.with`, `kotlin.synchronized`, `kotlin.io.use`, `kotlin.use`) and a `recordDiscardedLambdaValue()` helper so the IR transformer's existing `discardedCalls` tracking (used to suppress the **boolean inversion** mutation operator on discarded results) also walks into these six stdlib scope-function lambdas. This is purely a **mutation-generation precision fix inside one operator** (fewer equivalent/unkillable mutants on an existing idiom) — it changes which mutants `@MutFlowTest`/`MutFlowRunner`/the KMP native runner discover, not any build-time API, task, dependency, or DSL surface.

Nothing in the diff touches `mutflow-gradle-plugin`, `mutflow-junit4`, `mutflow-junit6`, `mutflow-core`/`mutflow-runtime`, `gradle.properties`, or `DESIGN-MULTIPLATFORM.md`.

## 7. Script-behavior read: intentional guard, one cosmetic nuance

`scripts/check-upstream.py:95-110` runs, in source order: (1) the Maven Central stable-version loop that appends the two "Upstream X stable is 1.6.1" errors (`:99-101`); (2) the `gradle.properties` Kotlin-pin check (`:102-106`, did not fire here); (3) the `compare/v{version}...master` call and its "Upstream master differs" error (`:107-109`); (4) an **unconditional** `print(f"Verified upstream mutflow v{version}, release commit {comparison['base_commit']['sha']}")` (`:110`) — this runs whether or not step 1 or 3 appended errors, since it is not gated on `errors` being empty. Only after all of this does `if errors: ... raise SystemExit(1)` (`:112-115`) flush the queued messages to stderr and fail the step.

Because the workflow redirects both streams to one file (`python3 scripts/check-upstream.py > upstream-status.txt 2>&1`, `.github/workflows/upstream-sync.yml:21`) and Python buffers stdout but not stderr when stdout is not a TTY, the stderr `[upstream] ...` lines reach the file before the already-queued stdout `Verified...` line is flushed at interpreter exit — exactly the order seen in the issue body. This is a **stdio buffering artifact, not a logic defect**: the exit code and the detection of drift are both correct. The wording is the only arguable issue — `"Verified upstream mutflow v1.6.0, release commit ..."` reads like a clean-bill-of-health line but is actually just naming the commit used as the comparison's base, printed unconditionally. A maintainer polish item (not a functional bug) would be to gate that print on `not errors` or rename it to something like `"Compared against upstream mutflow v{version}, release commit {sha}"` so it can't be misread as contradicting the three failures above it.

## 8. Answering the parent's three hypotheses

- **"Intentional monitor alert"** — confirmed; this is exactly what `scripts/check-upstream.py:2`'s docstring says it does, and the workflow's issue-filing step is a deliberate, separate, `if failure()`-gated step (`.github/workflows/upstream-sync.yml:25`).
- **"Actual 1.6.1 compatibility issue"** — not supported by any first-party evidence found. The diff is scoped to one mutation operator inside the compiler plugin (§3); `gradle.properties` and all three consumer POMs (`mutflow-gradle-plugin`, `mutflow-junit4`, `mutflow-junit6`) pin identical Kotlin/JUnit/JUnit4 versions at both tags (§4); the README's JUnit 6/JUnit 4/KMP integration description is untouched by the diff (§5). The only user-visible effect of upgrading is that a narrow class of previously-generated equivalent mutants (boolean inversion on discarded `let`/`run`/`with`/`synchronized`/`use` results) will no longer be produced — a strictly-fewer-false-positives change for existing suites, not a breaking one.
- **"Unreleased-master-only noise"** — partially right, precisely qualified: `master` carries **no commits beyond the tagged, Maven-published `v1.6.1`** (§6: `compare/v1.6.1...master` is `identical`, 0 commits). So the third message isn't flagging hidden unreleased drift; it is a mechanical restatement of the same, already-documented 1.6.0→1.6.1 gap, and will clear itself once/if the pin is bumped to `v1.6.1`.
