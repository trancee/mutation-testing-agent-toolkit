# Is MutFlow 1.6.2 Compatible, and What Does Its Serialization-Generated-Code Fix Change?

**Date:** 2026-10-06
**Research only.** No pins, implementation, tests, or other toolkit files were modified while producing this note, and nothing was committed or pushed. This note is itself the only artifact created.

**Trigger:** Continuation of the `mutflow-kmp-upstream-review` series (`01-kmp-dependency-variant-resolution.md`, `02-v1.6.1-compatibility-review.md`) for the toolkit's ongoing migration off MutFlow 1.6.1. Upstream `anschnapp/mutflow` tagged **`v1.6.2`** at commit `0f6dfe91a79fc96464e8fbf85817d539b3c71f65` on 2026-10-05, containing a single fix: mutation generation no longer mutates code the `kotlinx.serialization` compiler plugin (or, generically, any other compiler plugin) generates into a target class. ## 3. What the fix does, precisely — verified against the Kotlin compiler, not just the PR description

CHANGELOG (`anschnapp/mutflow:CHANGELOG.md` at `v1.6.2`, [permalink](https://github.com/anschnapp/mutflow/blob/0f6dfe91a79fc96464e8fbf85817d539b3c71f65/CHANGELOG.md)):
> "Code that the kotlinx.serialization plugin generates is no longer mutated. In a build that passes mutflow with `-Xplugin` alone, mutflow runs after that plugin and found its code in the target: the `write$Self` function of a `@Serializable` class, and, when a pattern such as `com.example.Event.**` also matched it, the `$serializer` object nested in the class. A class with two properties got nine mutants nobody wrote (...), reported on line 0 or on the class declaration. A class another compiler plugin declares is now never a target, and members with the serialization plugin's own origin are skipped like the compiler-generated ones. With mutflow on the compiler plugin classpath it runs first and never saw this code, which is why the sample module pins the order for its new `SerializableTarget`."

The code change, read directly in `mutflow-compiler-plugin/src/main/kotlin/io/github/anschnapp/mutflow/compiler/MutflowIrTransformer.kt` at the tag ([permalink base](https://github.com/anschnapp/mutflow/blob/0f6dfe91a79fc96464e8fbf85817d539b3c71f65/mutflow-compiler-plugin/src/main/kotlin/io/github/anschnapp/mutflow/compiler/MutflowIrTransformer.kt)):

- **`MutflowIrTransformer.kt:180-190`** — the pre-existing `compilerGeneratedOriginNames` set (already used since 1.3.2 to suppress mutation of data/value-class synthetic members, default property accessors, and delegation forwarders) gains one new literal at line 189: **`"KOTLINX_SERIALIZATION"`** — the exact origin name kotlinx.serialization's own compiler backend assigns to the `write$Self` function it builds (verified independently below).
- **`MutflowIrTransformer.kt:196`** — a new extension function: `private fun IrDeclaration.isGeneratedByPlugin(): Boolean = origin is IrDeclarationOrigin.GeneratedByPlugin`.
- **`MutflowIrTransformer.kt:336-385`, `visitClass`** — at lines 352-355, `isInMutationTarget` is now computed as `!declaration.isGeneratedByPlugin() && (declaration.hasAnnotation(mutationTargetFqName) || matchesTargetPattern(...))`. A generated class (e.g. the `$serializer` object nested inside a `@Serializable` class) is now **never** a target, even if a broad pattern like `Foo.**` would otherwise name it.
- **`MutflowIrTransformer.kt:387-410`, `visitSimpleFunction`** — at line 405, the existing "suppress this member's mutations" check becomes `if (isInMutationTarget && (declaration.origin.name in compilerGeneratedOriginNames || declaration.isGeneratedByPlugin()))`. A member another compiler plugin added to an otherwise-real target class (i.e. `write$Self`, which — unlike `$serializer` — is injected as a member of the author's own class, not a separate generated class) is now suppressed the same way compiler-generated data/value-class members already were.

**Independent verification that this rests on real, stable compiler API, not an invented hack** (I traced this myself in `JetBrains/kotlin`, resolved to its `master` HEAD at research time, `6e13569dcd6ef3255baaae9f83728349d61277e1`, since this is a moving ref):
- `IrDeclarationOrigin.GeneratedByPlugin` is a genuine class in the Kotlin compiler's own IR tree: `compiler/ir/ir.tree/src/org/jetbrains/kotlin/ir/declarations/IrDeclarationOrigin.kt:133-155` ([permalink](https://github.com/JetBrains/kotlin/blob/6e13569dcd6ef3255baaae9f83728349d61277e1/compiler/ir/ir.tree/src/org/jetbrains/kotlin/ir/declarations/IrDeclarationOrigin.kt#L133-L155)), documented as the origin for declarations introduced by a FIR plugin extension, with `name = "GENERATED[${pluginId}]"`. A GitHub code search for `GeneratedByPlugin` across `JetBrains/kotlin` shows it is already used by several official/first-party compiler plugins beyond serialization — `noarg`, `lombok`, `power-assert`, `compose`, `kotlin-dataframe`, `parcelize`, `js-plain-objects` — i.e. this is the compiler's standard, general-purpose "a plugin generated this" marker, not something fragile or serialization-specific.
- The literal origin name `"KOTLINX_SERIALIZATION"` that `write$Self` carries (and that mutflow now matches by string, the same way it already matched the other compiler-generated origin names) is defined at its exact source: `plugins/kotlinx-serialization/kotlinx-serialization.backend/src/org/jetbrains/kotlinx/serialization/compiler/backend/ir/SerializerIrGenerator.kt:49` ([permalink](https://github.com/JetBrains/kotlin/blob/6e13569dcd6ef3255baaae9f83728349d61277e1/plugins/kotlinx-serialization/kotlinx-serialization.backend/src/org/jetbrains/kotlinx/serialization/compiler/backend/ir/SerializerIrGenerator.kt#L49)):
  ```kotlin
  val SERIALIZATION_PLUGIN_ORIGIN = IrDeclarationOriginImpl("KOTLINX_SERIALIZATION", true)
  ```
  This confirms *why* the fix needed two separate checks rather than one: `write$Self` is built by the serialization plugin's own IR-backend code using its own named origin object (not an instance of `GeneratedByPlugin`), while `$serializer` (a separate nested class) is generated through the FIR-extension declaration-generation path and so is expected to carry the generic `GeneratedByPlugin` origin. I confirmed the `SERIALIZATION_PLUGIN_ORIGIN`/`write$Self` half directly in the compiler source (above); the `$serializer`/`GeneratedByPlugin` half I did **not** independently trace through kotlinx-serialization's FIR extension call sites — I rely on PR #38's own description plus the generic mechanism's well-attested existence for that specific half (flagged again in "Remaining gaps").

**The fix is origin-based, not order-dependent, which matters for the compatibility question in §5**: once a declaration carries a recognized "I did not write this" origin, it is excluded from mutation whether MutFlow's own IR pass runs before or after the plugin that generated the code. Previously, the only thing protecting a consumer was MutFlow's pass running *first* (so the not-yet-created code simply wasn't there yet to see) — true "by accident" whenever that happened to be the classpath order, true by observed behavior only for the one build shape the PR describes ("with mutflow on the compiler plugin classpath it runs first and never saw this code"). 1.6.2 makes the correct behavior structural instead of incidental.

## 5. Does this affect the toolkit's default compiler-plugin/classpath arrangement? No — verified by direct inspection, not assumption

This is the question that matters most for "is this upgrade safe." I read every toolkit Gradle file that applies either plugin, at `HEAD` (`eb15610a4b7b6d5099126a449254b1e9a9e7fa74`):

- **`sample/build.gradle.kts`** (`git show HEAD:sample/build.gradle.kts`) is the toolkit's **only** module applying `id("io.github.anschnapp.mutflow")`. Its `plugins {}` block is exactly `kotlin("jvm") version "2.4.20"` + `id("io.github.anschnapp.mutflow") version "1.6.1"` — **no** `kotlin("plugin.serialization")`, no kotlinx-serialization dependency, anywhere in this file.
- **`sample/buildSrc/build.gradle.kts`** and its canonical template **`.mutation-testing/mutation-results-src/build.gradle.kts`** are the toolkit's **only** files applying `kotlin("plugin.serialization")` + `kotlinx-serialization-json`. These are a separate Gradle **buildSrc** module (per its own header comment, *"This file makes the typed MutationResults module available to build scripts via buildSrc"*) that compiles build-logic to parse MutFlow's own JSON mutation report into typed Kotlin classes. It applies **no** `io.github.anschnapp.mutflow` plugin at all — it is not a mutation-testing target, and MutFlow's compiler plugin never runs against it.

Therefore: **the toolkit's existing, `HEAD`-committed default arrangement never puts both compiler plugins on the same Kotlin compilation unit's classpath.** The pre-1.6.2 bug — mutating `write$Self`/`$serializer` when MutFlow's IR pass sees kotlinx.serialization's already-generated code — had no module in which it could occur in this toolkit, exactly as the 1.6.0→1.6.1 boolean-inversion fix in note 02 touched nothing the toolkit's existing modules exercised. Bumping the pin is compatibility hygiene (staying current, picking up a real but not toolkit-triggered fix, keeping `scripts/check-upstream.py`'s drift monitor quiet), not remediation of an observed defect.

One nuance worth being precise about for anyone extending the sample later (e.g. a future KMP/JVM module with `@Serializable` DTOs under mutation test): `MutflowGradlePlugin` applies MutFlow's compiler plugin via the official `KotlinCompilerPluginSupportPlugin` SPI — the same mechanism `kotlin("plugin.serialization")` uses — so if a module ever did apply both, which one's IR extension runs first is a Kotlin Gradle Plugin / compiler-plugin-ordering question, not something I independently re-verified for the general case (see "Remaining gaps"). What **1.6.2 changes** is that this no longer matters for correctness: the origin-based check added in §3 protects a target class's hand-written code regardless of which plugin's IR extension ran first. Upstream's **own** regression test needed an explicit `-Xcompiler-plugin-order=org.jetbrains.kotlinx.serialization>io.github.anschnapp.mutflow` override specifically to **force** the previously-buggy order for the test itself — because, per the PR body, MutFlow's normal classpath-based application "runs first and never [sees]" the generated code anyway, which would make an un-pinned-order regression test pass vacuously whether or not the fix is actually present. This exact detail — and the fact the toolkit's own in-progress regression test already reproduces it correctly — is covered in §8.

## 8. Regression-test approach: already implemented in the working tree, and it correctly avoids the vacuous-pass trap

The task asked me to identify a useful regression-test approach for the toolkit sample "if warranted." It is warranted in principle (the toolkit has no coverage today of a module applying both compiler plugins together — confirmed by `grep -n "serializ" scripts/test-mutflow-integration.py` at `HEAD` returning nothing), and — as observed live in the working tree, not something I added — one is already being built, closely mirroring upstream's own fixture. I verified it rather than designing a parallel one:

- `scripts/test-mutflow-integration.py`'s existing JVM/JUnit 6 scenario fixture gains `kotlin("plugin.serialization") version "2.4.20"` and `kotlinx-serialization-json:1.11.0` in its `write(jvm, "build.gradle.kts", ...)` fixture (this fixture project is then run through the toolkit's own `bootstrap.sh install`, which is what actually inserts `id("io.github.anschnapp.mutflow") version "1.6.2"` into the same file — so the resulting, as-built Gradle module genuinely does combine both plugins, the exact shape §5 says the toolkit does not have today).
- A new `SerializableTarget.kt` fixture — `class SerializableTarget(val name: String, val count: Int = 0) { fun isEmpty(): Boolean = count == 0 }` — is byte-for-byte the same shape as upstream's own `mutflow-test-sample/src/main/kotlin/sample/SerializableTarget.kt`, and a new `SerializableTargetTest.kt` uses `@MutFlowTest`/`MutFlow.underTest` to exercise both `Json.encodeToString`/`decodeFromString` (reaching `write$Self` and the nested `$serializer`) and the hand-written `isEmpty()`.
- Critically, after `bootstrap.sh install` runs, the fixture's `build.gradle.kts` is appended with:
  ```kotlin
  tasks.withType<KotlinCompilationTask<*>>().configureEach {
      compilerOptions.freeCompilerArgs.add(
          "-Xcompiler-plugin-order=org.jetbrains.kotlinx.serialization>io.github.anschnapp.mutflow"
      )
  }
  ```
  This is the same flag, with the same plugin-ID ordering, that upstream's own `mutflow-test-sample/build.gradle.kts` added (§2/§5). Without it, per PR #38's own body, MutFlow's normal classpath-based application "runs first" and the test would pass regardless of whether the fix is present — i.e. it would look like coverage without being coverage. The in-progress toolkit test gets this exactly right.
- `mutflow { targets = listOf("fixture.SerializableTarget", "fixture.SerializableTarget.**") }` is appended (mirroring upstream's two target patterns — the class, and its nested `$serializer` via `.**`) immediately before the scoped run `gradle + ["-PmutationTest.includes=fixture.SerializableTargetTest", "mutationResults"]`, and the resulting report is asserted as:
  ```python
  assert serialization["totalMutations"] == serialization["killed"] == 1, serialization
  assert serialization["gaps"] == 0, serialization
  assert serialization["mutations"][0]["sourceLocation"].startswith("SerializableTarget.kt:"), serialization
  ```
  This mirrors upstream's own `SerializableTargetTest` assertion (`assertEquals(listOf("== → !="), mutations, ...)`) — exactly one real, hand-written, killed mutation, correctly attributed to a real source line in `SerializableTarget.kt` rather than line 0 or the class declaration (the symptom the bug produced). The pre-existing `Decision`/`Loop` fixtures in the same scenario carry `@MutationTarget` directly, so reassigning `targets` for this block does not remove their own coverage for the scenario's later steps (Gradle re-evaluates the whole, by-then-fully-appended build file fresh on each separate `gradle` invocation in this script, and class-level `@MutationTarget` is independent of the `targets` pattern list — verified directly against the `visitClass` logic quoted in §3).
- Scope observation, not a defect: this coverage is added only to the JVM/JUnit 6 scenario, not duplicated into the script's JUnit 4 or KMP scenarios. That is a reasonable choice — the fix operates at the IR/compiler-plugin level, independent of which JUnit integration orchestrates the test — but it does mean the KMP `jvm()` target path (which also runs MutFlow's compiler plugin) has no first-party serialization-interaction coverage of its own if that is ever considered valuable later.
